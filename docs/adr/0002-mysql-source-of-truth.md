# MySQL 为事实来源，Milvus 为可重建索引

## 背景

系统同时使用关系库（MySQL）与向量库（Milvus）。文档处理流程需要同时写入两处，存在双写一致性问题：任何一方失败、或二者内容漂移，都需要一个明确的仲裁方来决定"什么才是真的"。

## 决定

**MySQL 是事实来源（source of truth）**，存储 Document 记录、Chunk 正文与元数据、会话与消息；**Milvus 是可重建的检索索引**，即使被清空也可由 MySQL 全量重建。

双写顺序固定为：**先写 MySQL 取得 chunk 主键 → 以该主键派生 Milvus 主键写入向量库**。

## 理由

1. **可恢复性**：向量库出问题（版本升级、collection 损坏、索引参数调整）时，只需从 MySQL 重跑一次 embedding 即可恢复，不存在"数据只有向量库有"的险境。
2. **主键天然幂等**：Milvus 主键由 MySQL 自增 id 派生（`{doc_id}_{chunk_index}`），重试入库时按 `doc_id` 先删后写即可保证幂等，无需额外的去重机制。
3. **符合职责分工**：关系库擅长结构化查询、事务、状态机；向量库擅长近邻检索。让 MySQL 持有权威数据，Milvus 只做它的索引，是各自的强项。
4. **代价可接受**：chunk 正文在 Milvus 中冗余一份，用于检索后免去回表，属于为延迟付的合理冗余。

## 后果

- 检索时可直接从 Milvus 取回 chunk 全文，MySQL 不必参与在线检索路径。
- 冗余带来"两处正文可能不一致"的风险，但因 MySQL 权威且 Milvus 可由其重建，该风险被限定为"重建即可修复"。
- **注意**：本决定是"Milvus 中的 chunk 正文冗余"的正当性来源，后续若有人主张删掉该冗余，需重新评估。
