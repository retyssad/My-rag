# 意图识别采用「软注入」而非「硬路由」

## 背景

为提升检索针对性，系统在检索前引入意图识别，把问题分为四类：`product_qa`（商品咨询）、`policy`（售后政策）、`compare`（商品对比）、`chitchat`（闲聊）。

分类结果如何作用于检索，有两条路线：

- **硬路由**：每个意图走各自独立的检索/生成路径（如 policy 只查政策文档、compare 走专门逻辑）。
- **软注入**：意图只调整统一检索链路的参数，始终回退到 hybrid 检索。

## 决定

采用**软注入**。意图分类结果只做以下三件事：

| 意图 | 动作 |
|---|---|
| `policy` | 注入 `doc_type=policy` 过滤，**但取「过滤 + 全量」的并集**（`union_unfiltered`），不排他 |
| `compare` | 扩大 `dense_top_k`/`sparse_top_k` 至 ≥40、`rerank_top_n` ≥8，并开启按文档去重（`diversify_by_doc`，每篇最多 1 个 chunk） |
| `chitchat` | 短路：不检索，直接生成寒暄回应 |
| `product_qa` | 保持默认，不修改任何参数 |

唯一的"路由"行为是 `chitchat` 的短路——因为对闲聊而言"不检索"本身就是正确的处理。

分类器失败（超时、JSON 解析失败、异常）时兜底为 `product_qa`，即最中性的默认。

### policy 为何必须取并集（实测教训）

初版把 `policy` 实现为**硬过滤**（只保留 `doc_type=policy`）。实测发现：2 条商品类 FAQ（"屏幕碎了保修吗""丢了单只耳机怎么办"）被分到 `policy`，其正确文档（FAQ）被硬过滤排除，直接漏召，导致整体 R@5 反而下降 1.5pt。

这暴露了硬过滤与"软注入"哲学的矛盾：排他性过滤一旦误判就必然漏召，没有兜底。改为**并集**（过滤结果优先，全量结果补充）后，正确文档回到首位，同时政策文档仍被优先考虑——召回不再可能低于 baseline。这使意图识别成为"零风险的小优化"而非负收益。

## 理由

1. **失败代价可控**：软注入下，分类错误的后果是"参数白调了"，检索仍会正常返回结果。硬路由下分类错误会直接走到错误的链路，且没有兜底。
2. **保护可量化卖点**：本项目的核心资产是检索环节的消融表（dense / sparse / hybrid / +rerank）。软注入保留了统一检索链路，因此新增意图识别后，仍可在原有框架上直接对比 `hybrid+rerank` 与 `+intent` 两档（见 `run_eval.py` 的 `hybrid_rerank_intent`）。硬路由会让之前的消融表失效。
3. **与评估集分层自然对应**：gold set 的 `filter` 层对应 `policy`、`cross` 层部分对应 `compare`，软注入的增益可在既有分层上观测。
4. **识别准确率有限时更安全**：实测分类准确率 0.971（macro-F1 0.932），仍有边界误判（如"屏幕碎了保修吗"在商品问题与政策之间模糊）。软注入使这些误判不会造成明显退化。

## 后果

- 意图识别是"检索参数的一个优化器"，而非一条独立链路；相应地，它的价值主要体现在 `filter` / `compare` 类问题上，对占比最高的 `simple` 商品问答几乎无影响。
- `chitchat` 短路节省一次完整检索，并避免"空上下文硬答"。
- `compare` 的按文档去重发生在 rerank **之前**，以保证候选池含多个文档、rerank 有跨文档的选择空间。
- 由于软注入改变了 `doc_type` 过滤，评估 `+intent` 档时必须让 `use_intent` 成为消融配置的显式开关（其它档位置为 False），否则无法归因。
- 首轮问答会增加一次 `qwen-turbo` 调用（约 0.3–0.5s 延迟）。
