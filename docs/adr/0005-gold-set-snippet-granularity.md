# 评估集的 gold 标注到文本片段，而非 chunk id

## 背景

项目需要用 recall@k / MRR 量化检索链路各环节的增益，因此需要一份 gold set（标准答案集）。标注粒度的选择直接影响评估集寿命：若标注"某 query 的正确 chunk id 是哪些"，则一旦切分策略改变，chunk id 全体失效。

而"对比不同切分策略/参数"本身就是计划中的实验之一，两者存在根本冲突。

## 决定

gold set 中每条 query 的相关性标注为 **`(doc_id, 目标原文片段)`**：记录相关文档的主键，以及该文档中命中答案的那段原文文本；**不记录 chunk id**。

评估时以**文本匹配**判定命中：检索返回的 chunk 若包含（或充分重叠于）目标片段，即视为该 chunk 相关。相关性判定在 **doc 粒度与 chunk 粒度**上分别计算。

## 理由

1. **解耦切分实验**：标注绑定原文而非切分产物，因此可以自由地更换切分器、调整 `chunk_size` / `overlap`、改动表格旁路策略，而无需重标注 gold set。
2. **可复现性**：原文字段随语料一并提交进仓库，任何人 clone 后都能复现同一评测结果，不依赖本地数据库状态。
3. **贴近真实评测语义**：检索的目标本就是"找到包含答案的文本"，chunk 只是实现手段。按文本内容判定，指标衡量的是系统能力而非切分偶然性。
4. **容错**：文本重叠匹配可以容忍 chunk 边界略微偏移，避免因切分边界差几个字而误判为未命中。

## 后果

- 需要实现一个片段匹配函数（归一化 + 包含/重叠判定），并处理同一片段被切到多个 chunk 的情况（此时多个 chunk 均可判为相关）。
- 必须**固定语料原文**：gold set 与语料库强绑定，语料一旦修改，相关标注需同步复核。语料文件因此随仓库提交。
- 该决定使"切分策略消融"成为可能，是评估方案成立的前提。
