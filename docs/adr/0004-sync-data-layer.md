# 数据访问层同步，仅 LLM 流式为异步

## 背景

FastAPI 支持 `async def` 与 `def` 混合端点。数据访问层（SQLAlchemy、pymilvus）与模型调用层（百炼 SDK）都可以选择同步或异步实现，混用会带来复杂度，需要统一取向。

## 决定

- **数据库（SQLAlchemy）与向量库（pymilvus）使用同步 API**；相关 FastAPI 端点用 `def` 定义，由框架自动调度到线程池。
- **LLM 流式调用使用异步**（`AsyncOpenAI` / 异步 SDK），以支撑 SSE 逐 token 输出。
- 异步仅存在于"生成"这一段；检索与入库全流程同步。

## 理由

1. **延迟结构决定取舍**：RAG 的延迟长尾在 LLM 生成（秒级），保证其不阻塞事件循环即可；DB 与向量检索均为毫秒到百毫秒级，同步调用丢线程池完全够用。
2. **调试成本**：异步 SQLAlchemy（`aiomysql`）与 `AsyncMilvusClient` 的会话管理、连接池、异常传播都更复杂，出问题时排查成本高。
3. **工期约束**：项目为 3~4 周的作品集，把时间花在检索质量与评估上，收益远高于把数据层改成异步。
4. **入库路径天然适合同步**：文档入库是后台任务，批间串行 + 重试退避的同步写法更直观、更易保证幂等。

## 后果

- 端点函数签名需注意：涉及 DB/向量库的用 `def`，涉及 SSE 的用 `async def`，二者不可混用（在 `async def` 里调用同步阻塞代码会卡住事件循环）。
- 若未来并发压力显著上升，需要重新评估该决定（届时优先考虑给阻塞调用加 `run_in_threadpool` 而非全面异步化）。
