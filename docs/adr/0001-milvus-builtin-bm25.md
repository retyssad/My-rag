# 混合检索的稀疏路径用 Milvus 内置 BM25，融合用库内 RRFRanker

## 背景

系统需要「稠密向量检索 + 关键词检索 + 融合」的混合检索。向量库选型为 Milvus（见 ADR-0006 版本 pin）。最初的设计倾向于在应用层用 `rank_bm25` + `jieba` 自行实现关键词检索与 RRF 融合，理由是「过程完全可控、便于逐环节消融」。

后续核实（2026-09-27）推翻了该理由的两条前提：

1. **Milvus 2.5+ 内置完整的稀疏检索能力**：文本字段设 `enable_analyzer=True` + 定义 `FunctionType.BM25` 映射到 `SPARSE_FLOAT_VECTOR` 字段，稀疏索引为 `SPARSE_INVERTED_INDEX`（`metric_type=BM25`，`bm25_k1`/`bm25_b` 可调）。分析器需**显式指定中文**：`analyzer_params={"type": "chinese"}`。实测若省略该参数，默认分析器对中文几乎无效，中文短查询的 BM25 检索返回 0 条，稀疏路径形同虚设。
2. **`rank_bm25` 已基本停止维护**（2024 年后无功能性提交，README 自述大规模生产建议改用其他包）。

因此「自己做才可控」不再成立：库内实现同样暴露 `k1`/`b`，且依赖处于维护中。

## 决定

- **稀疏（关键词）检索**：使用 Milvus 内置 BM25（`enable_analyzer` 文本字段 + `FunctionType.BM25` + 稀疏向量索引）。
- **融合**：使用 Milvus `hybrid_search` 配合 `RRFRanker`（`k=60`）。
- **应用层不再引入** `rank_bm25` / `bm25s`，也不自行实现 RRF。
- 应用层仍通过 `RetrievalConfig` 控制**单路 vs 混合**：分别调用 `search`（仅稠密）或 `search`（仅稀疏）作为对照基线，调用 `hybrid_search` 作为混合路径，从而支撑消融实验。
- Rerank 仍由应用层调用百炼 `qwen3-rerank` 完成（不在 Milvus 内）。

## 理由

1. **依赖健康**：库内实现处于维护中，避免为停维库背负自研与维护成本。
2. **消融粒度足够**：核心卖点是量化融合增益，而 `dense-only / sparse-only / hybrid` 三档已能完整证明「融合是否有效」。库内融合不削弱这张表的说服力。
3. **工程信号**：选用现代栈的既有能力而非重造轮子，是更强的工程判断力体现；面试追问 RRF 时，能说明「RRFRanker 的 k 值、与加权融合的取舍、以及单路对照结果」同样到位。
4. **中文分词一次配置即可用**：`content` 字段声明 `analyzer_params={"type": "chinese"}`，即可获得可用的中文分词，省去应用层分词与词典维护。**注意**：不指定时中文检索不可用，这是必须写进 schema 的一行配置。

## 后果

- **不再需要「启动时全量加载 chunk 到内存构建 BM25 索引」**，也无需在文档入库后重建内存索引——稀疏索引由 Milvus 随写入维护。此前设计中相关的一节作废。
- Milvus 中必须**同时存在**稠密向量字段与稀疏向量字段（同一 collection），文本经 `FunctionType.BM25` 自动生成稀疏向量，因此正文必须在 Milvus 内可读（与 ADR-0002 中「chunk 正文在 Milvus 冗余一份」的决定一致且互相支撑）。
- **代价**：融合发生在库内，若未来需要「自定义融合算法」或「跨库融合」，需回到应用层实现，届时重开此决策。
- 该决定**替代了本项目早期草案中「应用层 rank_bm25 内存索引」的方案**，原因是其前提经核实不成立。
